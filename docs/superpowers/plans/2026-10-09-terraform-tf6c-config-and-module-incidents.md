## Review Focus

1. `-target` plans and applies exactly what real Terraform would (the targets and their dependencies; destroy mode includes dependents), prints the real warnings, never silently changes root-only untargeted behavior, and cannot be used to bypass the world-based fix/trap logic (a partial apply is recorded in history like any apply) (Task 1).
2. A hand-edited lock file now fails the way real Terraform does (cached package vs lock), `init`/`init -upgrade` repair it, `terraform providers` shows the real tree, and default scenarios are untouched (Task 2).

4. Each incident teaches a distinct skill and the debrief makes only claims the docs support (reviewer check per task).
5. Ids, evidence tags, command-library ids and files do not collide with existing incidents/commands (Task 8).

### Task 5: `terraform-provider-lock-drift` (the lock file no longer matches the constraint)

**Files:** Create `content/iac/terraform-provider-lock-drift.yaml`, `tests/terraform-provider-lock-drift.test.ts`; modify `CONTENT_TODO.md`, library entries.

**Story.** A PR bumps `required_providers` to `~> 5.50` to get a bug fix; CI fails on `terraform plan` with `Error: Inconsistent dependency lock file` because `.terraform.lock.hcl` was not updated (it still records 5.31.0). **Design.** Mounted own `.terraform.lock.hcl` (5.31.0, constraint `~> 5.0`) in `terraform.files`; `terraform.providers: { aws: { lock: "5.31.0", available: ["5.31.0","5.50.0","5.67.0"] } }`; the PR's config constraint `~> 5.50`. Evidence (simulator output): plan error text; `terraform version` (locked version); `terraform providers` (constraint tree); scripted `git diff` (the bump). Fix: `terraform init -upgrade` (world: lock records ≥5.50, cache matches, `plan_clean`): `done_when: all[ plan_clean, file_contains <lock file> version = "5.67.0"-style anchored regex, not: file_contains (main.tf) revert of the constraint ]`; second route: revert the constraint in `main.tf` to `~> 5.0` (credited? it makes the plan clean without upgrading: decide: it is a legitimate way to unblock but defeats the PR's purpose → NOT credited as the fix; credit via `file_contains` requiring the constraint to remain `~> 5.50` or higher). Wrong (world-detected through `file_contains` on the lock): hand-editing the lock version without `init` → the cached-package error; the trap (destructive) here is mild: choose `terraform apply` with the lock bypassed? There is no bypass; so make the destructive trap a button-only action ("delete `.terraform.lock.hcl` and `.terraform` and start over: loses the recorded hashes") detected by `file_contains`? A deleted file cannot be detected by file_contains (unreadable → false). Author: pick the closest world-detectable mistake (e.g. `init -upgrade -lockfile=readonly` conflict error teaches; a trap that matters in the real world is pushing a hand-edited lock); explain the choice in the report; the plan's rule "destructive trap detected from the world" may be satisfied by a `wrong` action detected by `file_contains` if no destructive world effect exists, but a `destructive` button-only trap must be justified in `CONTENT_TODO.md` as in `terraform-sg-cycle`.
